# Internacionalización: idioma, zona horaria y moneda

Norma única de i18n de la API. Sustituye a `docs/internationalization.md`.

## Qué resuelve

Para cada petición, job o correo, la API sabe tres valores **efectivos**:

| Valor | Guardado en | Herencia (gana el primero) |
|---|---|---|
| Idioma (`locale`) | `users.locale`, `tenants.locale` | usuario → tenant → cabecera `Accept-Language` → instalación |
| Zona horaria (`timezone`) | `users.timezone`, `tenants.timezone` | usuario → tenant → instalación |
| Moneda (`currency`) | `tenants.currency` | tenant → instalación |

`NULL` en una columna significa **heredar**. La instalación se configura en `config/i18n.php`
(`.env`: `APP_LOCALE`, `I18N_LOCALES`, `I18N_DEFAULT_TIMEZONE`, `I18N_DEFAULT_CURRENCY`, `I18N_CURRENCIES`).
Sin multiempresa activo el escalón «tenant» no existe. La cabecera solo aporta el idioma, y solo si es uno de
`I18N_LOCALES` (`es-PE` cuenta como `es`; con calidades gana el primero soportado).

## Resolver: `LocaleResolverInterface`

Se inyecta por interfaz (`App\Contracts\LocaleResolverInterface`):

```php
$resolver->locale();      // 'es'
$resolver->timezone();    // 'America/Lima'
$resolver->currency();    // 'PEN'
$resolver->localeFor($user, $tenant); // sin cabecera: para correos y jobs
$resolver->effective();   // los tres + supported_locales, para exponer al front
```

No guarda estado: lee el usuario del guard `api`, el `TenantContext` (scoped) y la petición, cada vez.

## Idioma de la petición (Octane)

`App\Http\Middleware\SetApiLocale` es **global** (también cubre 404/405 sin ruta):

1. Fija `App::setLocale()` con el idioma resuelto y responde `Content-Language`.
2. `ResolveTenant` lo reaplica al conocer el tenant (el middleware `tenant` va después de `auth:api`).
3. Al terminar, **restaura el locale anterior en un `finally`** (también si hay excepción). Octane mantiene el
   proceso vivo: sin esa restauración, el idioma de una petición se filtraría a la siguiente.

Los errores siguen llevando su `code` estable (`ErrorCode`): el front traduce por `code`; `message` sale en el
idioma resuelto y es informativo.

## Traducciones (`lang/`)

- `lang/es` y `lang/en`: `auth`, `pagination`, `passwords`, `validation` (+ `attributes`) y `messages`
  (errores del handler global, respuestas de i18n y correos).
- **Paridad obligatoria**: `tests/Unit/LangParidadTest.php` falla si a un idioma de `I18N_LOCALES` le falta
  una clave, le sobra una o cambian los marcadores `:x`. Un idioma nuevo = carpeta `lang/<código>/` con todos
  los archivos + añadirlo a `I18N_LOCALES`.
- Mensajes nuevos de la API o de un correo: `__('messages.…')`, nunca texto fijo. Los Form Requests ya no
  llevan mensajes comunes propios (`BaseFormRequest` los toma de `lang/validation.php`); un mensaje específico
  de un campo debe ir también en `lang/` si tiene que salir en varios idiomas.
- Los mensajes de éxito y de excepciones de dominio escritos como literales en controllers y servicios existentes
  siguen en español; se migran a `lang/` al tocar cada módulo.

## Correos y notificaciones en cola

`User` implementa `HasLocalePreference` (`preferredLocale()` = usuario → tenant del contexto → instalación, **sin
cabecera**). Laravel aplica ese idioma al enviar `notify()` y `Mail::to($user)`, también desde la cola: el
correo sale en el idioma del destinatario, no en el de quien dispara el job, y el locale del worker se restaura.
Para un destinatario que no es `User`, usa `->locale($resolver->localeFor(null, $tenant))`.

## Zona horaria: solo presentación

- **BD y API siguen en UTC**: columnas `timestamp`, JSON en ISO 8601 con offset. No se llama a
  `date_default_timezone_set` (es estado global del proceso).
- La zona efectiva se usa para: mostrar fechas (`->setTimezone($resolver->timezone())`), correos, y calcular el
  **«día»** de un usuario o empresa (reinicios diarios o anuales, cierres, informes): `now($tz)->startOfDay()`.
- Se expone al front con `GET /user/locale` (`effective.timezone`) y en el perfil.
- Validación: identificador válido de `DateTimeZone::listIdentifiers()` (regla `timezone:all`).

## Moneda

`tenants.currency` (código ISO 4217, mayúsculas) validada contra `config/currencies.php`, la misma lista que
usa `Money` (`docs/money.md`). `I18N_CURRENCIES` (opcional, separada por comas) la restringe a las que ofrezca
tu SaaS; una moneda fuera de `config/currencies.php` nunca se acepta. La moneda de un importe concreto sigue viajando con el importe; esta es solo la **por defecto** del tenant.

## Endpoints

| Método y ruta | Quién | Efecto |
|---|---|---|
| `GET /user/locale` | usuario autenticado | `stored` (lo guardado, `null` = hereda) y `effective` |
| `PUT /user/locale` | usuario autenticado | `locale`, `timezone` (cada uno `null` para heredar) |
| `PUT /user/profile` | usuario autenticado | también acepta `locale` y `timezone` |
| `GET /tenant/locale` | miembro del tenant (`tenant` middleware) | ídem para el tenant |
| `PUT /tenant/locale` | `permission:tenant-settings.manage,api` + rol `owner`/`admin` **en ese tenant** (`TenantRoles::actorRankFor`) | `locale`, `timezone`, `currency` |

Sin multiempresa activo `/tenant/locale` responde 400 `tenant_required`. Un tenant solo ve y cambia el suyo
(`TenantContext::require()`; no recibe ids).

`user.preferences.lang` y `user.preferences.timezone` (JSON de `PUT /user/preferences`) son anteriores y **no
se usan** para resolver: usa `users.locale` / `users.timezone`.
